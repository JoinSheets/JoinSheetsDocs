JoinSheets — приложение без сборки: нет бандлера, нет build-шага, нет CI. Релиз —
это осознанное, ручное действие: слияние накопленных изменений в `main`,
упаковка и тег — а не что-то, что происходит при каждом пуше. Эта страница
описывает, как это устроено.

## Версионирование

- Релизы помечаются тегом на конкретном коммите в `main` (имя тега — сама
  версия, например `0.2.0b1`).
- JoinSheets сейчас в фазе **бета**: нумерация версий продолжает ту же схему,
  что использовалась на этапе альфы, только вместо `a` — `b`: `0.1.0b1`,
  `0.2.0b1` и так далее.
- Бета-фаза подразумевает небольшие, постепенные изменения: доработки UI/UX,
  время от времени — новые функции, без резких архитектурных скачков.

## Веткование

- `develop` — ветка повседневной работы. `main` всегда остаётся чистым,
  готовым к релизу снимком — без тестовых наборов и вспомогательных скриптов
  разработчика, только то, что нужно самому продукту для работы.
- Релиз — это слияние `develop` в `main`, при этом артефакты разработки
  (тесты, тест-раннер и т.п.) в это слияние намеренно не попадают.
- Крупные изменения сначала попадают в `develop` через собственные
  короткоживущие ветки; это не жёсткое правило без исключений, но поведение
  по умолчанию.

## Что входит в релиз

Каждый релизный коммит в `main` добавляет один архив
(`JoinSheets-<версия>.tar.gz`) в корне репозитория — снимок продакшн-файлов
релиза (код + демо-данные, без тестов, без содержимого submodule). Архив
предыдущей версии не хранится — историю версий хранят её собственный тег и
страница GitHub Release, а не файл в дереве репозитория.

Тот же самый архив публикуется и как asset на странице
[GitHub Release](https://github.com/JoinSheets/JoinSheets/releases) этой
версии, вместе с описанием изменений. Пока проект в фазе бета, релизы
помечаются как `prerelease: true`.

Фактический список изменений по каждому релизу, а также план на следующий —
в [CHANGELOG.md](https://github.com/JoinSheets/JoinSheets/blob/main/CHANGELOG.md).

## Хотфиксы

Небольшое, низкорисковое визуальное или поведенческое исправление, найденное
вскоре после релиза, не обязано ждать следующего планового релиза — оно может
пойти прямо в `main` и сразу же быть перенесено в `develop`, чтобы не
потеряться (или не вернуться обратно) при следующем слиянии `develop`. Это
решение по ситуации, а не автоматический процесс: что-то, затрагивающее
больше нескольких строк или требующее полноценного тестирования, ждёт
обычного релиза.

Такой хотфикс не обязательно сразу получает собственный свежий архив и
GitHub Release — упакованные артефакты подтягиваются на следующем настоящем
релизе, который включает в себя всё накопленное, включая хотфиксы.

## Ночная версия (nightly preview)

Отдельно от всего вышеперечисленного: собственный `build.sh` сайта
[joinsheets.github.io](https://joinsheets.github.io/) при каждом запуске
собирает сразу два варианта — официальный сайт (с живым демо, закреплённым на
последнем релизном теге) и вторую копию демо-приложения, собранную из
текущего состояния `develop`, опубликованную по адресу
[`/nightly-demo/`](https://joinsheets.github.io/nightly-demo/). Она нигде не
указана ссылкой на сайте и исключена из индексации поисковиками через
`robots.txt` — доступна по прямому адресу, но нигде не рекламируется.

Это не шаг подготовки релиза и не обязательная проверка, которую что-либо
должно пройти — это рабочий инструмент повседневной разработки, запускается
когда угодно, независимо от того, готовится ли релиз. Его главная польза: он
ловит два типа проблем, которые не видны при чисто локальном просмотре —
визуальные/UX-огрехи, заметные только когда реально смотришь на
отрендеренную страницу, и особенности конкретной среды — например,
собственное CDN-кеширование GitHub Pages, которое локальный Hugo-сервер
просто не воспроизводит.
