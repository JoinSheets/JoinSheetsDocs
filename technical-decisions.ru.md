[Функциональные требования](../functional-requirements/) отвечают на
вопрос, *что* должен делать JoinSheets. Эта страница — о том, *как*: о
технических требованиях, стоящих за этим, и о конкретных решениях,
которые их удовлетворяют.

## Технические требования

Эти ограничения — не деталь реализации, а требования сами по себе, и именно
они формируют каждое решение ниже:

- **Безопасность и зеро-траст.** У приложения нет бэкенда и нет системы
  учётных записей, которой нужно доверять или которую можно
  скомпрометировать — на сервере нечего атаковать, потому что сервера нет.
- **Локальная работа.** Работает целиком на клиенте, в том числе прямо по
  `file://` — без установки, без серверного процесса, без шага сборки перед
  запуском.
- **Работа в закрытом контуре.** Для функционирования приложения не
  требуются исходящие запросы какого-либо вида — оно должно полноценно
  работать в изолированной сети, без какого-либо сетевого выхода вовне.
- **Отсутствие зависимостей.** Приложение поставляется как собственный
  законченный набор файлов, без необходимости что-либо подтягивать, чтобы
  оно заработало.

**Единственный компромисс:** одна внешняя зависимость —
[SheetJS](https://sheetjs.com/) (`xlsx.full.min.js`, Community Edition),
используемая опциональным конвертером
[JoinSheetsImport](https://github.com/JoinSheets/JoinSheetsImport) для
чтения `.xlsx`-файлов. Она вшита (vendored) в репозиторий с фиксированной
версией, под собственным файлом лицензии, и никогда не подтягивается с CDN
или любого другого внешнего ресурса — ни на этапе сборки, ни во время
работы нет ничего, куда нужно было бы обращаться, в том числе для её
обновления.

## Реализация

- **Без сборщика, без фреймворка.** Каждый модуль — небольшой IIFE в духе
  UMD, дописывающий себя в `window.DS_APP` в браузере и экспортируемый через
  `module.exports` под Node для тестов — см. хелпер-гиперскрипт `el()` в
  `util.js`, самый нижний слой.
- **Данные загружаются как обычные скрипты.** Источники — обычные
  `.js`-файлы, инжектируемые через `<script>` (а не `fetch()`, который
  `file://` блокирует), дописывающие себя в общее пространство `window.DS`.
- **Один стор + редьюсер** (`store.js`), разбитый на доменные редьюсеры по
  префиксу действия (`preset/*`, `group/*`, `table/*`, ...), с диспетчем
  через небольшой pub/sub (`createStore`).
- **Ленивый columnar-формат источников**: каждый файл источника описывает по
  функции на поле, возвращающей значения этого поля для всех строк
  позиционно — V8 не материализует тело функции, если она не вызвана, так
  что неиспользуемые поля ничего не стоят при загрузке.
- **Формулы, а не `eval`.** Расчётные поля используют небольшой
  самописный токенайзер/парсер/вычислитель (`formula.js`), осознанно не
  `eval`/`new Function`, поскольку пресеты — обычные JSON-файлы, которыми
  люди обмениваются.

## Тестирование

Модули с чистыми функциями (`dataset.js`, `entities.js`, `formula.js`,
`export.js`, `store.js`) — именно поэтому в архитектуре жёстко разделены
логика и код, трогающий DOM: это и даёт возможность чисто покрыть их
юнит-тестами `node:test`. Как реально запускать набор тестов — см.
[Тестирование](../testing/).
