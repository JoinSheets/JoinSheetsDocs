Этот раздел описывает принятую на проекте систему тестирования, основные
виды тестов, используемые инструменты тестирования. Перед тем как открывать
pull request убедитесь, что сделанные изменения ничего не сломали.

У JoinSheets нет автоматизированного CI — полный набор тестов запускается вручную
перед обновлением очередного релиза. Хорошим тоном является самостоятельный
запуск тестов перед открытием pull request — это дает минимальную страховку
от внезапных падений во время слияния версий и появления неявных конфликтов.

## Юнит-тесты

Для юнит-тестов используется обычный [`node:test`](https://nodejs.org/api/test.html)
(встроенный тест-раннер Node, без зависимости от тестового фреймворка), в `tests/`.
Скрипт для запуска полного набора:

```bash
./run_tests.sh
```

(тонкая обёртка над `node --test tests/*.test.js` — явный список файлов, а
не рекурсивный поиск, чтобы тесты опционального submodule `import/` не
попадали в этот прогон).

| Файл | Покрывает |
|---|---|
| `dataset.test.js` | Объединение источников, условия отбора, расширенный фильтр, сортировку. |
| `entities.test.js` | Парсинг чисел/дат/булевых значений, типизацию, разрешение коллизий — самая рискованная логика в приложении: граничные случаи (Excel-даты в виде serial-номера, неоднозначные разделители) проще всего сломать правкой «на глаз». |
| `export.test.js` | Экспорт в CSV/Excel и построение имени файла экспорта. |
| `formula.test.js` | Токенизатор/парсер/вычислитель формульных полей. |
| `preset.test.js` | Нормализацию пресета и редьюсер стора — самый большой файл, поскольку большинство пользовательских действий — это кейсы редьюсера. |

Это тесты на чистых функциях: ни `document`, ни `window` и ничего, связанного с DOM.

## Smoke-тест

Отдельная, вторая проверка: `tests/smoke/dom-smoke.js`. Он реально
прогоняет последовательность `<script>` из `index.html` — настоящий
бутстрап, настоящие `sample-data/` — внутри минимальной самодельной
DOM-заглушки (без `jsdom`, без npm-зависимостей; ровно столько
`document`/`window`/`sessionStorage`/`requestAnimationFrame`, сколько нужно
для одного прохода от загрузки до экрана Table).

Он ловит то, что юнит-тесты структурно не видят: забытые экспорты,
неправильный порядок `<script>` в `index.html`, сломанную
ленивую межмодульную ссылку. Запуск:

```bash
node tests/smoke/dom-smoke.js                   # обычная загрузка -> Table
node tests/smoke/dom-smoke.js --simulate-crash   # восстановление после сторожевого таймера краша
```

Этот вид тестов не подхватывается `node --test`/`run_tests.sh` —
имя файла не совпадает с их шаблоном автообнаружения, поэтому запускать его нужно отдельно.
Это не замена настоящему браузеру: если изменение затрагивает DOM API,
которого нет в заглушке (настоящий `querySelector`, CSSOM,
`getBoundingClientRect`, реальный клик), тест не поймает этот вид багов —
здесь всё ещё требуется ручная и визуальная проверка в браузере.

В будущем планируется расширять этот вид тестирования на более
широком охвате тесткейсов.

## Перед открытием PR

1. Запустить `./run_tests.sh` — все тесты зелёные — это минимальная планка.
2. Запустить smoke-тест в обоих режимах (`node tests/smoke/dom-smoke.js`).
3. Для всего, что касается DOM/UI, который не проверяется smoke-тестами —
   открыть `index.html` в браузере, проверить руками и глазами.
4. Написать тесты на то, что изменилось. Фикс без регрессионного теста, или
   новый кусок логики без покрытия — это незаконченная работа —
   `preset.test.js` и `entities.test.js` хороший пример того, как выглядит
   полноценное покрытие для кейсов редьюсера и граничных случаев
   парсинга/типизации соответственно.

## Тесты и релизы

Полный набор (и юнит-тесты, и smoke-тест в обоих режимах) прогоняется перед релизом,
и должен пройти успешно, прежде чем изменение попадёт в релиз — см.
[Релизы](../releases/).
